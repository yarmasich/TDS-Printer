# TDS Printer Server

FastAPI бэкенд — **только JSON API**. Веб-интерфейс живёт отдельно в
`../frontend/` (Vue 3 + Vite), бэк его не отдаёт. Так бэкенд можно
переиспользовать (мобильный клиент, скрипты, другой фронт), а фронт
деплоить независимо.

## Что это

Заменяет per-планшетный SharedPreferences одним центральным сервером в
локальной сети. Все шаблоны, авторизации, причины и история печати живут
в одной БД. Печатает сам — рендерит битмап (PIL) и шлёт raw TCP на принтеры.

## Текущее состояние (MVP)

- [x] FastAPI + SQLite
- [x] CRUD: шаблоны, причины, авторизованные операторы, история печати
- [x] Веб-UI: Print Panel (`/`) и Admin (`/admin`)
- [x] Печать по TCP: JScript / EPL2, проверка геометрии и калибровки
- [x] Excel импорт + поиск
- [x] Admin login (JWT, env credentials)

## Запуск

```bash
cd server
python3 -m venv .venv
source .venv/bin/activate
pip install -e .
cp .env.example .env              # задайте ADMIN_* (см. ниже)
alembic upgrade head              # создаёт / мигрирует БД
uvicorn app.main:app --host 0.0.0.0 --port 8000 \
    --reload --reload-dir app --reload-dir alembic
```

### Admin login

Панель `/admin` и изменяющие API (шаблоны, импорт, CRUD проектов и т.д.)
требуют JWT после `POST /api/auth/login`. **Print** и **Kiosk** требуют логин станции после создания первой станции
в Admin → Stations; до этого сохраняется прежний режим без входа.

Файл `server/.env` (см. `.env.example`) подхватывается при старте uvicorn
автоматически:

- `ADMIN_USERNAME` — логин
- `ADMIN_PASSWORD` — пароль
- `ADMIN_JWT_SECRET` — случайная длинная строка для подписи токена

Без этих переменных вход в админку отключён (на экране login будет предупреждение).
После правки `.env` перезапустите uvicorn.

Чтобы посмотреть UI — поднимите фронт отдельно: `cd ../frontend && npm run dev`,
откройте `http://localhost:5173`.

### Печать из внешнего приложения (API-ключ)

Стороннее приложение может печатать по номеру кабеля через
`POST /api/v1/print` с заголовком `X-API-Key` (без логина в админку). Ключи
выдаются в админке → раздел **API keys**. Полная документация с примерами —
[`docs/external-print-api.md`](docs/external-print-api.md).

Эндпоинты:
- `GET /` — служебный JSON-баннер (`{service, docs, openapi, health, frontend}`)
- `GET /docs` — Swagger
- `GET /openapi.json` — спека (фронт качает её для генерации типов)
- `GET /health` — `{ok: true}`
- `GET /api/*` — REST

> ⚠️ **Важно**: с обычным `--reload` uvicorn смотрит **весь cwd**, включая
> `data/tds.db`. Каждая запись в SQLite меняет mtime файла — uvicorn
> перезапускается прямо в момент транзакции, остаются хвосты от прерванных
> писем и SQLite начинает возвращать `attempt to write a readonly database`.
> Поэтому всегда передавайте `--reload-dir app --reload-dir alembic` (или
> запускайте без `--reload` в продакшне). И обязательно из активированного
> venv — `source .venv/bin/activate`, иначе пойдёт системный uvicorn.

Страница печати и админка доступны на адресе фронтенда (обычно порт 5173).
`http://localhost:8000/docs` — Swagger бэкенда.

## Миграции БД (Alembic)

Источник истины для схемы — модели в `app/models.py`. Любое изменение
модели надо превращать в миграцию.

```bash
# Применить все накопленные миграции (нужно при первом запуске и после git pull)
alembic upgrade head

# После того как поменяли модель — сгенерировать миграцию
alembic revision --autogenerate -m "add foo to template"
# Откройте сгенерированный файл в alembic/versions/, прочитайте, поправьте если надо

# Накатить
alembic upgrade head

# Откатить на 1 ревизию
alembic downgrade -1

# Текущее состояние
alembic current

# Полный список
alembic history
```

SQLite поддерживает только ограниченный `ALTER TABLE`. У нас включён
`render_as_batch=True` — alembic эмулирует ALTER через CREATE-COPY-DROP, так
что большинство правок (rename column, change type, add NOT NULL, …) работают.
Сложные случаи (например, изменение типа FK) могут потребовать ручной правки
миграции.

Стартап-хук `init_db()` мы убрали — теперь схемой управляет **только** alembic.
Если запустить uvicorn до `alembic upgrade head` — будут 500-ки на запросах к БД.

## Развёртывание на mini-PC / Raspberry Pi

1. На сервере (Raspberry Pi OS / Ubuntu) поставить Python 3.11+.
2. Скопировать проект, `pip install -e .`.
3. systemd unit:
   ```
   [Unit]
   Description=TDS Printer Server
   After=network.target

   [Service]
   ExecStart=/path/to/.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000
   WorkingDirectory=/opt/tds-server
   Restart=always
   User=pi

   [Install]
   WantedBy=multi-user.target
   ```
4. На каждом планшете: установить **Fully Kiosk Browser**, указать homepage
   `http://<server-ip>:8000/`, включить landscape lock + immersive.

## Следующие шаги

1. **Print engine**: порт `PandaRawPrinter.buildPrintJob` на Python (PIL для
   рендеринга текста, ручная упаковка 1-бит растра, `socket` для отправки
   на `ip:port`). См. `app/printer.py`.
2. **Импорт XLSX**: `openpyxl` для парсинга, перенос полей из `XlsxReader`.
3. **Поиск**: `SearchFilters` + индексы по `LabelRow`.
4. **Авторизация**: cookie-сессии + PIN.
5. **Миграция данных с планшетов**: одноразовая команда, читающая
   SharedPreferences старого APK и заливающая в БД.


## Ограничения доступа и ресурсов

Print/Kiosk и операторская печать остаются без пароля. Не открывайте backend
напрямую в публичный интернет: ограничьте его доверенной сетью/VPN или
аутентификацией на reverse proxy. CORS не заменяет контроль сетевого доступа.

`CORS_ALLOWED_ORIGINS` задаёт разрешённые браузерные origins через запятую,
например `https://print.example.com,http://localhost:5174`. Указывайте схему,
хост и при необходимости порт, без пути, завершающего `/` и `*`.
По умолчанию список пуст: UI и API должны работать через один origin.
Vite уже проксирует `/api`, поэтому для обычной локальной разработки менять
настройку не нужно. Некорректный список останавливает запуск сервера.

Вход ограничен 10 попытками с одного адреса и 100 попытками на процесс за
60 секунд, включая успешные входы. При превышении: `429` и `Retry-After`.
Ограничитель хранится в памяти, сбрасывается при рестарте и независим у каждого
worker. Для нескольких workers используйте общий лимит на reverse proxy.
Приложение не читает `X-Forwarded-For` самостоятельно: настройте доверие к
proxy в ASGI-сервере только для известных адресов proxy.

Лимиты одного XLSX (загрузка и сканирование каталога):

| Переменная окружения | По умолчанию |
| --- | ---: |
| `TDS_IMPORT_MAX_FILE_BYTES` | 26214400 (25 MiB) |
| `TDS_IMPORT_MAX_UNCOMPRESSED_BYTES` | 104857600 (100 MiB) |
| `TDS_IMPORT_MAX_ARCHIVE_ENTRIES` | 1000 |
| `TDS_IMPORT_MAX_SHEETS` | 100 |
| `TDS_IMPORT_MAX_ROWS` | 100000 |

Все значения — положительные целые числа. Лимит строк общий для книги,
включает заголовки и пустые строки. Превышение возвращает `413`, повреждённый
XLSX — `400`; неудачный импорт откатывается. Ограничение файла проверяется
после multipart-парсинга, поэтому отдельно ограничьте входящий HTTP body:
например, `client_max_body_size 26m;` в Nginx для upload, с учётом multipart
обвязки. Эти настройки proxy приложение само не устанавливает.

Для защиты внешней печати от повторов передавайте `Idempotency-Key` в оба
эндпоинта интеграции; правила повторов описаны в
[External Print API](docs/external-print-api.md#safe-http-retries-with-idempotency-key).
Перед запуском новой версии примените `alembic upgrade head` после резервной
копии БД. Резервации запросов сохраняются в БД и автоматически не удаляются.

### RFID перед печатью

После резервного копирования БД выполните `alembic upgrade head`. Новая настройка
`require_rfid` по умолчанию выключена: существующие проекты продолжают работать.
В Admin → Projects включите RFID для нужного проекта. Print и Kiosk запросят карту
перед отправкой всей очереди; считыватель вводит номер и завершает ввод Enter.
Если в очереди несколько проектов и хотя бы один требует RFID, проверяется весь пакет.
Имя из ручного поля Operator не заменяет обязательную проверку на сервере.
Внешняя печать через `/api/v1/print` и `/api/v1/print-batch` с API-ключом
освобождена от RFID: журнал фиксирует `api:<имя ключа>`, без подтверждения RFID
и без employee_id. Настройка проекта действует на операторскую печать Print/Kiosk.

В QR Attendance откройте Settings → System → External Employee API как
активный super administrator и создайте отдельный ключ `TDS-Printer` с доступом
к нужным проектам. Ключи FloorHub и других приложений не переиспользуйте.
Сохраните выданный один раз токен только в серверном secret store. При ротации
создайте новый ключ, обновите сервер, проверьте интеграцию и отзовите старый.

Настройте в серверном окружении `RFID_API_URL` (полный адрес
`https://your-host/api/v1/external/employees`) и `RFID_API_TOKEN`, затем
перезапустите сервер. Для организации с публичным префиксом используйте, например,
`https://attendance.example.com/acme/api/v1/external/employees`. Нужны оба
значения: при отсутствии URL или ключа сервер сообщает, что интеграция не
настроена, и не обращается к каталогу. Приложение выполняет GET с параметрами `rfid`,
`active=true`, `limit=2`, `offset=0` и заголовком `Authorization: Bearer <token>`.
Пример ответа HTTP 200:

```json
{
  "items": [{"employee_id": "employee-123", "rfid": "0012AB", "full_name": "Alice Able", "active": true, "project": {"id": 10, "name": "Chicago"}, "subcontractor": null}],
  "total": 1, "limit": 2, "offset": 0
}
```

Принимается только одно совпадение с активным сотрудником и совпадающей картой.
Ведущие нули сохраняются; знаки пунктуации и пробелы удаляются, буквы приводятся
к верхнему регистру. Исходный ввод ограничен 256 символами, результат — 64.
Пустая карта, отсутствие совпадений, уволенный сотрудник, несколько совпадений
или некорректный ответ блокируют печать. `active` не проверяет присутствие на смене.

Каталог целиком не загружается и не кешируется. Внешний `project_id` не
подставляется из нашего ID проекта: пространства идентификаторов независимы.
Доступные сотрудники определяются областью действия внешнего API-ключа.
Поля внешнего проекта и подрядчика не заменяют проект задания печати.

Используется HTTPS (HTTP разрешён только для loopback-разработки), таймаут
5 секунд; перенаправления запрещены. Адрес интеграции и секрет задаются только
на сервере. При недоступности API или ограничении частоты запросов печать не
отправляется и автоматически не повторяется. После устранения ошибки нужно
снова отсканировать карту. Номер карты не следует включать в access-логи
внешнего API и его reverse proxy: lookup использует query-параметр `rfid`.

История сохраняет стабильный `employee_id`, имя сотрудника на момент операции, источник имени, признак
RFID-проверки, проект, время, принтер и результат каждой попытки. Номер карты
не сохраняется в журнал или БД. Admin → History позволяет фильтровать период,
проект и точное имя; итоги считаются по всему периоду, независимо от последних
200 записей в таблице. Итоги RFID группируются по `employee_id`, поэтому смена
имени или карты не создаёт нового сотрудника, а однофамильцы не объединяются.
Старые записи без ID не связываются автоматически по имени. Счётчик показывает попытки отправки строк (обычно пары
наклеек), а не подтверждённое физическое количество отпечатков. Неопределённый
результат выделяется отдельно. Старые записи не получают RFID-подтверждение задним числом.

Прямая печать шаблона без исходной этикетки и изменение её текста через прямой
endpoint требуют авторизации администратора. Обычная операторская печать
проверяет политику проекта исходной этикетки.

### Panduit TDP43ME по сети

В Admin → Printers выберите модель **TDP43ME**, укажите IP принтера и порт
RAW TCP (обычно 9100; должен быть включён на самом устройстве). Профиль выбирает
EZPL и 300 dpi. Windows-драйвер на сервере Linux не нужен: приложение формирует
растровое задание и отправляет его непосредственно принтеру.

Архив `PRINTER DRIVERS V5.3.10.zip` содержит драйвер NiceLabel/Panduit
5.3.10.7633 для TDP43ME, TDP43HE и TDP46HE. Наличие этих моделей в архиве не
означает, что им подходит один протокол: профиль здесь добавлен только для TDP43ME.
Спецификации производителя: 300 dpi, максимальная ширина печати 105.7 мм,
длина этикетки 12–762 мм, язык EZPL. Приложение использует консервативный предел
1248 точек для TDP43ME; перед отправкой проверяется, что текст помещается.

Старое значение протокола `epl2` сохранено для совместимости и теперь называется
в интерфейсе **Legacy EZPL**. Оно исторически генерировало EZPL-команды с
фиксированными настройками. Существующие принтеры автоматически не переводятся
на новый профиль. В новом профиле размеры подачи берутся из шаблона; перед
производственной печатью проверьте ориентацию, подачу и калибровку на одной
наклейке. Программные тесты не подтверждают работу конкретной прошивки и
сетевого интерфейса — требуется физическая проверка. Команды подачи передают
миллиметры с точностью до 3 знаков; поддержку дробной подачи конкретной прошивкой
TDP43ME необходимо подтвердить на реальной наклейке.

Источники: [Panduit TDP43ME manual](https://www.panduit.com/content/dam/panduit/en/products/media/5/25/725/3725/111163725.pdf),
[EZPL Programmer’s Manual](https://godex.com.ua/components/com_jshopping/files/demo_products/EZPL_EN_I_02-1601.pdf).


### Несколько ноутбуков и принтеров: логины станций

После обновления примените миграции (`alembic upgrade head`) с предварительной
резервной копией БД. В Admin → Stations создайте отдельный логин для каждого
рабочего места, задайте пароль и назначьте принтер. Откройте Print или Kiosk на
ноутбуке и войдите под этим логином. Пример: `station-1` → Printer A,
`station-2` → Printer B, при этом обе станции выбирают одну дисциплину GPU-MS.

Дисциплина и шаблон общие: они определяют содержание и оформление этикеток.
Физический принтер определяется учётной записью станции на сервере и имеет
приоритет над принтером шаблона. Калибровка применяется для фактического
принтера и выбранного расходника. Подмена printer_id в клиентском запросе не
даёт станции права печатать на другом принтере. Принтер шаблона остаётся
значением по умолчанию для прежнего режима и других разрешённых сценариев.

Корзины изолированы по учётной записи и сеансу браузера; Print и Kiosk сохраняют
отдельные корзины. Для двух операторов используйте два логина. После создания
первой станции анонимная операторская печать блокируется, даже если все станции
затем отключены. Администратор по-прежнему может войти в Admin для настройки.
Пароли хранятся только в виде защищённых хешей, операторские токены не дают
доступ к административным изменениям. Отключение станции и смена пароля
отзывают её сеансы. Не переносите старую корзину автоматически на другой логин.

RFID остаётся отдельным подтверждением сотрудника перед печатью по настройке
проекта. В истории раздельно видны сотрудник, станция и фактический принтер;
доступен фильтр по станции. Внешняя печать `/api/v1` с API-ключом продолжает
работать независимо от логинов станций и не требует RFID.

Разные принтеры могут принимать задания параллельно. Отправка на один IP/порт
сериализуется существующей блокировкой на одном сервере приложения; это не
гарантия строгого FIFO и не подтверждение физического выхода наклейки.
При недоступности выбранного принтера задание не перенаправляется на другой.
